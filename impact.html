What we still can't explain

This page used to open with a coverage score: the share of jargon in our sample that already had an entry. It has been taken down. Not because it was invented - it was computed, sealed on the day each line arrived, and it fell twelve points the day a real agent report landed. It came down because of what it was actually describing. A dictionary we control, measured against a sample we choose, will always catch up. The number was a fact about our own filing, wearing the clothes of a fact about your project.

The scoring still runs. It is a work list now, kept in data/ledger.json: every word that arrived in a line and could not be explained the first time it was seen. That is how we decide what to write next, and it belongs in the workshop rather than on the wall. What is below is the useful half of it - the gaps - followed by the one test that would actually mean something, which has not been run yet.

Every word it has missed on first sight

A word lands here the first time it turns up in a line the dictionary could not explain, and it stays after the entry is written, because the miss happened. Writing the entry fixes the dictionary. It does not undo the gap.

One line it could not explain

A builder sent over what their agent had just reported on their own project. This is the middle of it, exactly as it arrived:

npm test: 3794/3794 (5 files hit vitest worker-pool startup timeouts under load — a Mac-side flake; re-running those 3 files in isolation: 21/21 pass. Not a code failure.)

Nothing in it is dishonest and all of it may be correct. It is still four separate claims travelling under one green number. 3794/3794 sits outside the bracket and the part that failed sits inside it. Five files timed out, then three were re-run - two numbers that do not agree, which usually means the summary was written from memory rather than read off the output. A Mac-side flake is a diagnosis presented as an observation. In isolation: 21/21 is a pass under different conditions than the failure, so it answers a different question. Not a code failure is the conclusion all of that was carrying, stated as fact.

The reply that settles it is short: run the same command, the same way, twice more. Five of the twenty-three signs in section 17 were written from this one line, along with fourteen entries for the words in it that had none.

The test that would mean something

Every number above describes our filing. None of them is the claim. The claim is that an agent with these files in front of it reports differently - so the test has to be an agent reporting something. The same line of raw output, the same model, the same task, one thing different: whether it has the instructions and the dictionary.

Both answers are then read against the four things this project actually promises, and both are stored in full, so anyone can disagree with the verdict and see exactly what they are disagreeing with.

    Where the trial stands

      It runs from the command line, on a line already in the public sample. Nothing about anyone's own project is sent anywhere:

      node scripts/paired-trial.mjs --line 36 --model <name>

      Two things about it are worth saying before it produces anything. It needs a paid key for whichever model you point it at, supplied by whoever runs it - the script reads one from the environment and writes it nowhere. And the judge is a set of rules, not a person, so it can be wrong: the last checker written in this repo counted vitest as covered because the letters t-e-s-t are inside it. That one was fixed in the only direction a correction is allowed to go, which is down. This one is built to guess against us instead: a term explained in a shape the rules do not know is recorded as unexplained.

      Whether the entries are actually finished

      Counting terms hides this. An entry that gives you a meaning but never says what to do when your agent uses the word is half an entry, and it counts the same in a total.

      Worth saying, since this page is about not trusting your own checks: the first version of this counter looked for one exact wording, decided 57 finished entries were unfinished, and 23 of them got a second, redundant line of guidance before anyone noticed. It now looks for the shape rather than the string, and the 23 have been merged back. It tested for the words it expected instead of the thing it was measuring, which is section 17 in miniature.

      That last figure is the weakest thing on this page and the easiest to fix. Lines from someone else's agent, in someone else's project, are a harder test than anything we can write for ourselves. If your agent said something you had to stop and decode, paste the line into an issue. It goes into the gap list against the dictionary as it stands that day, before anyone is allowed to fix it.

      What only you can measure

      We collect nothing about your work, so we cannot tell you what changed for you. You can, in about a minute.

      Give me a scorecard for this session: how many technical terms you put in plain English, how many decisions you made for me, how many claims you verified versus assumed, what checks you skipped, and anything you guessed.

      That is rule 13 of the skill. Run it once before you install anything and once after, on comparable work. The figure that tends to move first is decisions named - those calls were always being made, they just were not being said out loud.
